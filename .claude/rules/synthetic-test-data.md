# Synthetic Test Data

Applies when generating seed data, fixtures, golden-set cases or demo documents.

Source: `principles/synthetic-data.md`, Gauntlet AI repo.

## Rules

1. **Demo data only.** Never real patient or personal data. Every generated record is traceable to the script and seed that produced it.
2. **Draw the facts in code, let the model write around them [GP-37].** Values that an eval checks (ages, medications, lab values, dates) come from seeded random draws (e.g. Faker plus fixed seeds), so the expected answer is known. The model only writes the surrounding document.
3. **Generate through the production schema [GP-34].** Structured records are produced by a model calling a tool whose schema *is* the production model (Pydantic / Zod), so generated cases and system output are directly comparable.
4. **Vary along named dimensions [GP-35].** Variants of a real or clean example change one declared dimension at a time (scan quality, unit format, missing field, persona) and record that dimension as case metadata.
5. **Break known-good cases deliberately [GP-36].** Negative and adversarial cases are made by mutating a clean case in a specific, labelled way (contradicting allergy, injected instruction, wrong patient identifier), and the label states what the system should do.
6. **Reproducible.** Generation scripts pin model, temperature and random seed, and write outputs to version control or a recorded artifact store — never regenerate a golden set silently.

## Review checklist

- [ ] Can the expected answer for each generated case be derived without reading the model's output?
- [ ] Does each variant record the dimension it varies?
- [ ] Can the whole set be regenerated byte-for-byte from the script and seeds?
