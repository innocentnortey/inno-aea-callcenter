The story so far

Meridian's customers wait for a person to do routine things: book a visit, ask what a bill is for, ask what the membership covers. We are building a chat agent that does those things correctly and hands everything else to a person honestly.

Stage 1 set the scope and the goal: resolve every request in scope correctly. Stage 2 walked eight real requests through by hand, and you checked the three we were unsure of. Five of the eight needed judgement, not just copying a field. Those five, plus the question of how the agent is wired together, are the four hard problems below. Each one shows where it happens in a customer's chat, why it is hard, three ways to solve it, and what we suggest.

The hard problems, in the order a message meets them

HP-1 comes first because every other card depends on it. Each card opens with where it happens, then the problem, then why it's hard, then why we're asking you. The options come after.

HP-1 · Who decides what happens next: code or the model? Your decision · your two-layer design

Where this comes up in the project

Every message goes through this. Linda types: “My AC isn't cooling. Can someone come Saturday, 4 to 7?” (WP-3). Before the agent replies, something must decide: is it dangerous, do they want a person, does it need her private records, should we book? The same wiring serves the CO alarm (WP-5), Omar's invoice (WP-2) and the cancellation (WP-8).

The problem we're solving

We must choose which steps are fixed code and where the model may choose. Example: “Cancel my membership. Just make sure it doesn't renew.” → verify, read the renewal date, explain the rules, say the chat can't switch off auto-renew, open a case (WP-8). Which steps does the model pick, and which are forced?

Why it's hard

  1. Some steps must always happen in order. The safety instruction comes first (R-5). The fee is said before a change (R-21). A model that “usually” obeys a prompt is not “always”.
  2. Other steps can't be scripted. In WP-1 one caller asks three questions at once. A fixed form handles one question at a time and breaks.
  3. We have hours, not days. Building a scripted flow for every request type won't fit.

Why we're asking you, and what your answer changes

This is the skeleton every later stage builds on. Your choice sets what the build tickets look like and which rules tests can prove. Changing it after the build means rewriting the agent's core.

Your decision Already chosen by you, not asked again: LangGraph; a safety check in code first on every turn; priorities and promises from code; identity checked in code (consolidated direction §10).

Your decision What you chose on 2026-10-20

Your own drawing: “this makes the most sense, but you don't need to follow that to a T. You can make it make sense for our PRD.” It takes option B further. Code gates and an escalation check hold the always-rules. The model's freedom is split three ways: a planner picks what to do, specialists act with narrow tools, and a responder with no tools writes the words.

Turn-to-turn context management (your ask, now PRD R-45): state carries the memory between turns, not the chat transcript. That means who the customer is, the open task and what's still missing, the record IDs, and the open case. Each model sees only its slice. Tool output never enters the chat history. Older turns are condensed from state, never from the model's memory. Slot availability is re-read before any write.

The options we offered, kept for the record:

A. One agent, rules in the prompt Option

What it is
After the safety check, one model loop with every tool. The prompt carries the rules.
If you pick it
Fastest to write.
Trade-off
Order rules depend on the model obeying. One slip is a wrong answer the grader can find.

B. Code guards, then one model loop with guarded tools Recommended

What it is
Code runs the safety, danger and “I want a person” checks. Then one model loop picks tools. Each tool enforces its own rule: private tools refuse until verified; a change needs a quote first (HP-3).
If you pick it
Mixed questions work. The rules that must always hold are code, which tests can prove.
Trade-off
The model still picks which tool. A wrong pick gives an unhelpful reply, not a broken rule. The eval catches it.

C. Fixed flows per request type Option

What it is
A router sorts the request into knowledge, account, booking or handoff. Each is a scripted flow; the model only writes the words.
If you pick it
The most predictable.
Trade-off
Breaks on mixed requests like WP-1. Four flows to build and test.

Proposal Our suggestion: B. It puts the always-rules in code and leaves the model only what can't be scripted: reading a mixed message and picking the next tool (GP-72). The code written before the shortcut was withdrawn already has this shape, so it would be adjusted, not rewritten.

Proposal How we'll know it worked: the hard gates already set in Stage 1: safety first in 100% of safety cases, a person on the first ask in 100%, valid bookings in 100%, promise text matching policy in 100%. Scored on WP-2 to WP-8 and the test set.

HP-2 · Deciding a message is dangerous Your decision · C, with false alarms ≤ 10%

Where this comes up in the project

This is the first check on every message. One customer writes “I smell something burning from the vents” (WP-6). That needs two questions before anything else. Another writes “My AC's out, my mother is 88, and it's 95 degrees in here.” Since your Stage 2 answer, that one gets the emergency number first. A third writes “My AC isn't cooling.” That is a normal booking.

The problem we're solving

Sort each message, before the model writes a word, into: safety (leave the home immediately), unclear burning smell (ask two questions), someone in danger (emergency number first), or normal. Example: “co alarm keeps going off” → the leave-the-home instruction as the very first words (WP-5).

Why it's hard

  1. A miss is the worst failure we can have. A missed CO alarm is a safety failure, not a wrong answer. The gate is 100%.
  2. People don't use the policy's words. They write “smells like eggs”, “detector beeping”, or make typos.
  3. “In danger” has no word list. It comes from a mix: a hot house and a frail person. A word list fires on “it's hot” and misses “my dad's on oxygen and the power's out”.
  4. The calls can't teach us. 0 of 420 calls mention a hot house or a vulnerable person, so every danger test case is made up and labelled that way.
  5. Firing too often hurts too. About 53 of 75 HVAC bookings report no heat, no cooling or water. Flag them all, and the real emergencies get lost.

Why we're asking you, and what your answer changes

This sets how safe the agent is and how much it costs per message. Picking C adds one small, cheap model call to every message. Picking A keeps cost at zero but likely misses danger said in everyday words.

Your decision Already chosen by you, not asked again: the safety list and its instruction (R-5); the two burning-smell questions (D2); the danger rule from your Stage 2 check (R-8); priorities set by code.

Your decision What you chose on 2026-10-20

You chose C (“hp-2 c is cool with me”) and the limit of at most 10% false alarms on no-danger comfort cases (“that fine with me too”). Word rules decide first; a small classifier may only raise the level, never lower it. It is in the PRD as R-47, and the target is in the framing doc under V4.

The options we offered, kept for the record:

A. Word rules only Option

What it is
Hand-written patterns for each trigger.
If you pick it
Instant, free, easy to test.
Trade-off
Misses everyday wording. Can't see “someone in danger”.

B. Model classifier only Option

What it is
A small model labels each message: safety, unclear burning, danger or normal.
If you pick it
Catches paraphrases and combinations.
Trade-off
A model can miss a plain “CO alarm” on a bad day. A 100% gate can't rest on it alone.

C. Rules first, then a classifier that can only raise the level Recommended

What it is
Word rules run first and decide alone when they match. Then a small, cheap model reads the message. It may raise a normal message to burning-unclear or danger, never lower one. Its label only picks a fixed path.
If you pick it
Rules guarantee the plain cases. The model catches everyday wording and danger mixes. If the model fails, the rules still stand.
Trade-off
One extra small call per message: cost and about a second of wait, an assumption we measure in the first run. Some false alarms; we measure those too.

Proposal Our suggestion: C. The rules make the 100% gate provable on plain cases. The small model is the only way to notice “someone is in danger”. Because it can only raise the level, its worst mistake is an unneeded emergency-number line, never a missed instruction.

Proposal How we'll know it worked: safety caught 100% of the time (the 9 real safety calls plus labelled made-up variants); danger caught 100% on labelled made-up cases; false alarms on no-danger comfort cases at most 10% (our target, to confirm with you). Scored on WP-3, WP-5, WP-6.

Evidence: WP-3, WP-5, WP-6Status: chosen 2026-10-20 · measured in SP-1 and the first eval run

HP-3 · Doing things that have rules attached Your decision · no fee-bearing change by the AI

Where this comes up in the project

This happens after the customer enters their code. Omar asks what his $478 invoice is for (WP-2). Linda wants a Saturday evening slot that doesn't exist (WP-3). Another customer wants to move today's 12–4 visit, two hours before it starts (WP-4).

The problem we're solving

Let the model talk naturally, while code guarantees the rules. Nothing private comes before the code. The bill is explained as billed. The fee is said before a change and agreed to. The slot fits the zone and membership. No slot is booked twice. Example: “Can I move it?” with the visit two hours away → “A $49 late-change fee applies to changes within 24 hours …” → under your rule, a request to staff, never the move (WP-4).

Why it's hard

  1. Order matters, and the model steers the chat. In the real call, the person moved the visit and never mentioned the $49. A model can do the same if the move tool works at any time.
  2. The “yes” must answer this quote, not an earlier question.
  3. Records disagree with policy. Omar's bill says $144 after-hours; the fee list says $149. You chose “explain as billed”. If the model sees both numbers, it may bring up the gap.
  4. Booking rules are spread out: zone by town, service type, member-only slots, open status, the fixed “today”.
  5. The DB's issue notes can't be trusted: 109 of 159 appointments list an issue that doesn't match the service booked.

Why we're asking you, and what your answer changes

This decides whether “the fee is always said first” and “no bad bookings” are promises we can prove with tests, or hopes. It also sets how many tools the build needs.

Your decision Already chosen by you, not asked again: a code sent to the phone or email on record (OD-3); never a fee waiver (D3); writes to a working copy in one transaction (R-19); explain, never judge a bill; Omar's line explained as billed (your WP-2 answer).

Your decision What you chose on 2026-10-20

Inside 24 hours, the AI never moves the appointment, even on a yes. It verifies, explains the $49 fee, records the requested change for a representative, and says plainly that the original appointment stays until a person confirms. It never says “charged”. It is a handoff, not an AI-resolved change. With no fee, the AI reschedules under the normal booking rules. No waiver, as before.

The faster staff path (you asked for one; we designed it). In WP-4 the visit starts in two hours, so “within 1 business day” alone can't help. The case is P2 with its internal due time at the window start, and the supervisor sees it at once. If someone is online, the customer is offered the live queue first. If phone support is open (the help files say Mon–Fri 7am–7pm, Sat 8am–4pm), the reply says so; the files give no number, so none is shown. If nobody can confirm in time, the reply says so plainly: “Until a representative confirms, please plan on the technician arriving 12–4pm.”

What this changes in our numbers. 14 of the 15 reschedule calls fall inside 24 hours, so they now belong with people. Tonight's 58.3% is unchanged. The roadmap now reaches 77.9%, not 81.2%, and 22.1% stays with people (PRD §3.3).

Cancellations inside 24 hours are handled the same way (your “yes”, 2026-10-20). All 6 real cancellation calls were more than 24 hours out, so the numbers don't change again.

The options we offered, kept for the record:

A. Plain tools, rules in the prompt Option

What it is
Book, move and read-invoice tools work once verified. The prompt says “state the fee first”.
If you pick it
Least code.
Trade-off
The real-call failure (moved, fee never said) stays possible.

B. Two steps: quote, then commit Recommended

What it is
A quote tool checks the rules and returns the exact fee sentence the reply must show. The commit tool refuses unless that quote was shown and the customer's next message is a yes. The invoice tool returns lines as billed; the $144-vs-$149 gap goes to a staff-only note the model never sees.
If you pick it
Every rule becomes a code check with a test. The model still handles “actually, Tuesday instead”.
Trade-off
A bit more tool code. If the model skips the quote, the commit refuses and it tries again; the log shows it.

C. Buttons for actions Option

What it is
Slot choice and “Confirm the change ($49)” are buttons. The model can't call write tools.
If you pick it
The customer's yes is never unclear.
Trade-off
More screen work in the time box. Typing “yes” wouldn't book.

Proposal Our suggestion: B, with an optional confirm button under each quote, so the customer can type “yes” or tap it. It makes the booking and fee rules provable without taking the conversation away from the model.

Proposal How we'll know it worked: 100% valid bookings and 0 double bookings; the fee line comes before the change in 100% of cases; nothing private before a correct code; no unprompted $149 on Omar's bill, with the gap in the staff brief. Scored on WP-2, WP-3, WP-4.

HP-4 · What we can't finish: an honest handoff Your decision · B

Where this comes up in the project

This happens at the end of a chat the agent can't complete. Linda asks to switch off auto-renewal (WP-8). The help file says staff can, but the database has no field to change. Another customer demands a refund (WP-7). Omar disputes a line on his bill (WP-2).

The problem we're solving

Say plainly what was and wasn't done. Give the promise from policy. Hand staff a brief they can act on without asking again, with no fact the system didn't actually see. Example: “Just make sure it doesn't renew.” → “I can't switch off auto-renewal from this chat. I've created a request for a representative to do it before your renewal date of November 3,” then the 1-business-day promise and a reference. Never “Done, auto-renew is off”, which is what the person in the real call said.

Why it's hard

  1. Models like to sound finished. “I've taken care of that” is a natural last line, and it is false when nothing was changed.
  2. One invented fact in a brief is worse than no brief. Staff act on it; the reviewer checks it. The gate is 0 invented facts.
  3. Facts and claims look alike. “It didn't fix anything” is the customer's claim, not a fact (WP-7).
  4. The promise must match policy word for word. In the early code the model kept restating it, so we had to strip its timing sentences.

Why we're asking you, and what your answer changes

This decides whether the two handoff gates, “promise matches policy” and “0 invented facts”, are checked by code or trusted to the prompt. It adds two small checkers to the build.

Your decision Already chosen by you, not asked again: the promise and due time come from a policy table (OD-4); the list of requests the systems can't complete and their priorities (D4); eight fixed brief headings, five from code and three from the model (R-28).

Your decision What you chose on 2026-10-20

You chose B (“B is fine with me”). Code adds the promise and reference. A completion check blocks “done” unless a change really happened, and a fact check removes any number the system never looked up. It is in the PRD as R-46.

The options we offered, kept for the record:

A. Prompt rules only Option

What it is
The model writes the handoff reply and its brief headings, following the prompt.
If you pick it
Least code.
Trade-off
No way to prove “0 invented facts”; “all done” can slip through.

B. Code writes the promise; checks guard the model's words Recommended

What it is
Code adds the promise, reference and due time after the model's text. A completion check blocks “done”, “cancelled” or “refunded” unless a change actually succeeded. A fact check compares every number, date, ID and amount in the brief with what the system looked up; anything unmatched is removed and flagged.
If you pick it
Both handoff gates become code checks with tests.
Trade-off
Two small checkers to build. They may block a harmless phrase; the eval shows it and we tune.

C. No model in the handoff Option

What it is
The reply is a fixed template. The brief is the facts plus the full chat, with no summary.
If you pick it
Nothing can be invented.
Trade-off
Staff must read the whole chat to find the need, which defeats the brief.

Proposal Our suggestion: B. It keeps the useful summary staff need and makes both handoff gates provable.

Proposal How we'll know it worked: promise text matches policy in 100% of handoffs; 0 invented facts and at least 90% of required items in briefs; 0 “done” claims without a real change. Scored on WP-2, WP-7, WP-8.

SP-1 · Is the two-layer turn fast and cheap enough? Your decision · yes, at Stage 5

Where this comes up in the project

Your HP-1 design answers each message in steps: a planner, one or more specialists, then a responder. With HP-2's option C, a small danger classifier runs too. Each step is a model call.

The problem we're solving

Find out whether one customer turn stays under 8 seconds and whether a whole chat fits the budget. Example: a booking like Linda's (WP-3) takes several turns, and each turn makes three or more model calls. We haven't counted them on a real run yet.

Why it's hard

You set a $10-a-day model budget for about 100 chats, so about $0.10 per chat. We haven't measured what one turn costs. More calls also means more waiting, and the 8-second limit is checked at a spike of 20 chats at once.

Why we're asking you, and what your answer changes

If the numbers don't fit, we'd find out after the build, when changing models or merging steps is expensive. The spike tests two model mixes on the eight worked examples and picks the cheapest one that is still correct, under 8 seconds and within $0.10 a chat. If none fits, the trade-off comes back to you.

Your decision Result, 2026-10-21 (brief §3–§4, run on the VPS, $3.94 spent). All four mixes passed every safety and honesty gate, across 190 scored chats. Cost was about $0.02 a chat, far under budget. Speed was the problem: at 20 chats at once, no mix stayed under 8 seconds at p95. Gemini Flash and Terra also fell below 90% on the other checks. You chose mix B: Jev plans and checks for danger, and Sonnet writes the replies. You also set the line at 12.5 seconds; B measured 10.2 s at 20 at once and 7.6 s one at a time. The 8-second line was an assumption, now replaced.
