The story so far

Meridian Home Comfort is a fictional heating, cooling and plumbing company. We are building a chat agent that its homeowners talk to, and a staff console behind it. A homeowner writes that the heat has stopped. The agent answers from the company's own documents or books a visit. When it cannot finish the job, a person picks the case up. In the demo that person is Riley.

Two words you will see. A contract is a written agreement about one request between a screen and the backend: what the screen sends, what it gets back, and every way it can fail. If a screen can show a state, some contract must be able to produce it. A state is how a screen looks in one situation: empty, loading, in error, and so on. There are eight standard ones.

The mint decision

Mint means the customer's own words and choices, and nothing else Proposal

On the phone, mint marks the customer's turns (dr-26). On the console the look sheet put mint on the block "everything the assistant wrote" (dr-25's AI draft). The look sheet's assistant mark was also mint, so on the phone itself the assistant's mark and the customer's turns shared a colour. Staff will move between the two surfaces, and the customer's own words are exactly what a representative must tell apart from what the assistant said.

The alternative was to keep mint for "assistant-written" on the console and retint the phone's customer turns. That would have thrown away dr-26's clearest signal ("what I said / what they said") on the surface a stressed homeowner uses, to keep a signal on the console that a text label does just as well. Also, the promise is policy-table text, not model text (R-26), so tinting it as "AI-written" on the console would have been inaccurate. The authorship cue moves to words and the mark: the brief header reads "Brief written by the assistant" with the mark, and the promise card's header carries the mark and "Promise shown to the customer". What is lost: the console no longer has one coloured block that says "machine wrote this". What is gained: mint is a rule a reviewer can state in one sentence.

CON-2 is the main seam with the System track Proposal

Where this comes up. Every sentence the homeowner reads, and every card they tap, travels through one request, submitTurn. The screen sends a message or a choice. The backend sends back a list of "blocks" (a text answer, a slot card, a safety card, a handoff card) and a settled summary that fills the "What's settled" panel.

Why it is the seam. The System track owns what is true inside the reply: the model, the checks, the booking, the promise. UX owns how each block looks and which states exist. CON-2 is where both must agree exactly. A change on either side shows up here first.

  • 24 reply block types, each with a speaker and a time. The screen never invents wording for a fixed text such as the safety card or the promise: those arrive as words from code (UI_CONTRACTS.md CON-2).
  • Deadline 60 seconds, then a TURN_TIMEOUT card with Try again and Talk to a person. More than 30 replies in flight gets BUSY. No streaming and no progress events: the reply arrives whole. The target is p95 12.5 s; SP-1 measured 10.2 s with 20 chats at once.
  • settled is built from the whole conversation's completed writes, never only the last turn. A completion word like "booked" may appear only when the reply's writes[] or settled.actions says it happened.
  • Every refusal for a limit is still HTTP 200 with a notice and settled, so the panel stays true. "Talk to a person" (CON-4) works under every limit and is never disabled.

The data boundary Fact

The one-time code never reaches the model. It appears in exactly two places: the customer types it in a CON-2 code payload, and the demo inbox (CON-6) shows it. The backend compares it by code against a stored hash. The data-class table marks it D3 Secret: never to the model, never in logs and traces.

NOT_VERIFIED is identical for every cause. (no match, ambiguous, no contact): same sentence, same card, nothing that reveals whether an account exists. This is so that nobody can find out, by trying, whether an account exists.

Named errors, and what each screen does

An error is only useful if the screen knows what to say. The contracts keep two kinds apart. When the server decides what to say, such as "that window just went", it answers normally (HTTP 200) with an error block and the up-to-date summary.
