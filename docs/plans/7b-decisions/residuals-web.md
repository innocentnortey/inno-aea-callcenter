## For Innocent

### R-W-12 · Should a chat resume after the reviewer signs in again?

**The story.** The reviewer is mid-chat; their 12-hour login expires (or they sign out). SCREEN_SPECS SCR-1 (state
"Session ended while the chat is open") says that after signing in "the reviewer returns here and the chat resumes if it
is still open". The backend, as designed, starts a **new** login session at every sign-in (web.md §2) and gives each
thread to the session that opened it, so the earlier session's thread answers 404 to the new login (web.md §4
`owned_thread`). The browser keeps the thread id per tab, so after re-login it asks for the old thread, gets 404, and
starts a fresh chat. Nothing is lost on the server; the reviewer just sees an empty chat instead of their conversation.
AEA-58 tests only same-session refresh and leaves the re-login step out until this is settled. Cheap to change later:
one ownership rule in `owned_thread` plus one test.

**Option A: keep it as designed; SCR-1's copy changes to "sign in again to start a new chat".** No backend work; the
thread-per-login rule stays the simplest privacy boundary (one login cannot read another's chat). A copy edit for the UX
session.
**Option B: a thread belongs to the demo deployment's one login pair, not the login session; any session of the same
pair may resume it while it is open.** About two hours (ownership by a stable owner key on `conversations`, `owned_thread`
reads it, AEA-23/40 tests). Matches SCR-1 as written. Since R-48 has one login for everyone, "another session's thread"
stops being a boundary at all: any reviewer could open any open thread id they hold.
**Option C: carry the old session id into the new login (a resume hint), so only the browser that had the thread can
reclaim it.** About half a day; a new hand-over path to design and test.
*Recommended: A,* because with one shared login pair (R-48), B removes the only thread boundary, and C buys a small
convenience at real cost; the reviewer loses nothing stored.

**Decision needed:** After signing in again, should the earlier chat resume (B or C) or should the screen start a new
chat and say so (A)?
